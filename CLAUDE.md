# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev                   # dev server (Turbopack)
npm run build                 # builds changelog JSON, then next build - the main verification step
npm run lint                  # eslint via next lint
npm run build-equip-data      # regenerate public/equip-data/ from the WzDataExtractor dump
npm run build-map-data        # regenerate public/map-data/ from the WzDataExtractor dump
npm run verify-equip-tables   # data-integrity checks against public/equip-data/
npm run verify-equip-engine   # end-to-end checks of src/lib/equip/engine.js
```

There is no test framework. `npm run build` is the real check - it compiles every route and
prerenders the static ones, so it catches broken imports and SSR-unsafe code. The two
`verify-equip-*` scripts are hand-rolled assertion runners for the equip engine only; they are
the closest thing to a test suite, print a per-assertion pass/fail log with a failure count, and
exit non-zero on failure. `verify-equip-engine` currently has one pre-existing failure
(`Destiny stage 2 reaches 25*`), so compare against that baseline rather than expecting green.

On WSL, `next dev` can fail with `Permission denied (os error 13)` acquiring the Turbopack
lockfile. `rm -rf .next` clears it. `next start` on a production build is unaffected.

## Stack and conventions

Next.js 16 App Router, **JavaScript not TypeScript** (`.js` / `.jsx`; `pageExtensions` also
allows `.mdx`). React 18. Tailwind. `@/*` aliases `./src/*`.

Images use a **custom loader** (`imageLoader.js`) that bypasses Next's optimizer entirely -
local paths are served straight from `public/`, CloudFront URLs pass through untouched. `next/image`
still works, but `width`/`quality` do nothing. Several call sites pass `unoptimized` as well.

## Theming - use the CSS variable aliases

Colors are CSS custom properties defined in `src/app/globals.css` under `:root[data-theme='dark']`
and `:root[data-theme='light']`, exposed to Tailwind as named colors in `tailwind.config.js`.
`ModeToggle` flips `data-theme` on `<html>`.

Use `bg-background`, `bg-background-bright`, `text-primary`, `text-primary-bright`,
`text-primary-dim`, `text-secondary`, `border-primary-dim`, `progress-{red,orange,yellow,green}`.
Do **not** use raw Tailwind palette colors (`bg-gray-800`, `text-white`) for surfaces or text -
they don't invert with the theme. Arbitrary `hsl()` is fine where a value must be identical in
both themes (e.g. the burning field level ramp).

The `maplestory` font is applied globally, and there is a custom cursor image on `:root`.

## Feature structure

Each tool is a self-contained folder under `src/app/<feature>/`:

- `page.jsx` - server component, exports `metadata`, usually wraps a client component in
  `<Suspense>` (required when the client component reads `useSearchParams`)
- `components/` - the actual UI, `'use client'`
- tools that need to be linked from the homepage and hamburger menu get an entry in
  `src/data/navigationItems.js`; some (mystic-frontier) are deliberately unlisted

Several features persist UI state in the URL via `router.replace(...)` with `useSearchParams`,
so tabs and selections are linkable. Follow that pattern rather than adding local-only state
for anything a user might want to share.

## Where data comes from

Four distinct sources - pick the right one:

1. **Static game data** - plain JS modules in `src/data/` (`bossData.js`, `classes.js`,
   `mysticFrontierData.js`, …), imported directly and bundled.
2. **Large generated datasets** - JSON in `public/`, fetched client-side at runtime
   (`/equip-data/*.json`, `/familiar_data/*.json`, `/map-data/maps.json`, `/changelog.json`).
   Generated by scripts in `src/scripts/` from a **separate private repo**, `WzDataExtractor`,
   which mines the game client's WZ files. `docs/equip-compare-data.md` and `docs/map-data.md`
   document those schemas and the exact regeneration commands. Do not hand-edit these JSON
   files.
3. **Remote live data** - AWS API Gateway (`yaiphhwge8.execute-api.us-west-2.amazonaws.com`)
   backed by DynamoDB, plus assets on CloudFront (`dkxt2zgwekugu.cloudfront.net`). Used by the
   cash shop tool. `src/app/api/` holds only two thin edge routes (a Nexon ranking proxy and a
   Resend contact form).
4. **Supabase** - user-generated data for the interactive trackers, see below.

The changelog is authored as MDX in `src/content/changelog/` and compiled to
`src/data/changelog.json` + `public/changelog.json` by the prebuild step in `npm run build`.
Edit the MDX, never the JSON.

## Supabase

One Supabase project serves **all** features (`src/lib/supabase.js`, a single shared browser
client from `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLIC_KEY`). New features go in
that same project rather than a per-feature project - the shared auth user base is the point.

Auth is passwordless magic link (`signInWithOtp`) using the **implicit** flow, so tokens arrive
in the URL fragment. Each feature has its own `AuthProvider`/`LoginForm` pair that differs only
in `emailRedirectTo`. Local dev requires the localhost URL to be in the project's redirect
allowlist, or Supabase silently falls back to the production Site URL.

Two features use it, each with its own tables, RLS policies and `security definer` RPCs:

- `src/app/mystic-frontier/` - expedition logging (`expeditions`, `tiles`, `rewards`, `known_items`)
- `src/app/burning-field/` - per-channel burning level tracking, with groups and roles. Schema in
  `docs/burning-field-schema.sql`, design notes in `src/app/burning-field/README.md`,
  projection maths in `src/lib/burning/projection.js`.

Schema changes are applied by hand in the Supabase SQL editor - there is no migration runner. Keep
the `.sql` file in `docs/` idempotent and treat it as the source of truth.

## Game-domain logic lives in src/lib

Anything that encodes a MapleStory mechanic belongs in `src/lib/`, free of React and Supabase, so
it can be exercised from Node: `src/lib/equip/` (starforce, flames, potentials, set effects) and
`src/lib/burning/projection.js`. The `verify-equip-*` scripts import these directly. When adding a
mechanic, document the rule and its source in a comment or a README - the *why* behind a formula is
not recoverable from the code, and these rules change with game patches.

`src/lib/maps/catalog.js` is the same idea for game *content* rather than mechanics: it loads and
searches the extracted map catalogue behind the burning-field map picker.
